# Github Issue 작성 규칙

> 온디맨드 문서. `/github-issue` 스킬이 이슈를 작성할 때 읽는다.
> 양식은 `Docs/Template/Issues Template.md`를 따른다.

## 언어

- 이슈의 제목, 라벨, 본문은 모두 영어로 쓴다. (2026-11-09 결정)
    - 이유 : GitHub에서 이슈로 브랜치를 만들면 제목이 브랜치 이름이 되므로, Unity와 Git 도구에서 한글 브랜치 이름을 피한다.
- 문서 경로, 섹션 이름처럼 저장소 안의 한국어 이름을 가리킬 때는 원문 그대로 적는다.

## 제목

- 형식 : `[Type][Area] Summary`
    - 예 : `[Feature][UI] Build quest info popup`, `[BugFix][Map] Fix gap at east swamp border`
- 요약은 한 문장, 무엇을 하는지가 드러나게 쓴다. 동사로 시작한다.

## 라벨

- 유형 라벨 : `Feature`, `BugFix`
- 영역 라벨 : `UI`, `Map`, `Sound`, `Inspector`
- 저장소에 라벨이 없으면 Claude가 `gh label create`로 만들고, 만든 라벨을 사용자에게 알린다.

## 섹션별 규칙

### 유형, 담당 영역

- 하나씩 고른다. 여러 영역에 걸치면 이슈를 나눌지 사용자에게 묻는다.
- 게임 로직 스크립트는 사용자 담당이므로 Claude가 등록하는 이슈의 담당 영역이 아니다. 필요하면 "사용자 작업"으로 따로 적어 사용자에게 확인한다.

### 배경 (As-is)

- 지금 상태를 사실대로 쓴다. 추측은 "추측"이라고 표시한다.

### 목표 (To-be)

- 완료되었을 때 플레이어나 사용자가 보게 되는 결과로 쓴다.

### 작업 내용

- 체크리스트로 쓴다. 한 항목은 한 번의 작업 단위로 나눈다.
- 생성하거나 수정할 파일을 알면 함께 적는다.

### 완료조건 (DoD)

- 확인할 수 있는 조건으로만 쓴다. "잘 동작한다" 같은 표현은 쓰지 않는다.
    - 좋은 예 : "J를 누르면 의뢰 정보 팝업이 열리고, 열려 있는 동안 시점이 돌아가지 않는다"
- 유니티 에디터에서 사용자가 직접 확인해야 하는 조건은 "(사용자 확인)"을 붙인다.

### 버그 정보

- 버그수정일 때만 쓴다. 재현 방법은 순서대로 적는다.

### 참고 문서

- 관련된 `Docs/` 문서의 경로와 섹션 이름을 적는다.
