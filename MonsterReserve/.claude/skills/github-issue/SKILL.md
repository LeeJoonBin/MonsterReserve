# github-issue

개발, 버그수정 업무를 GitHub 이슈로 등록하는 절차다.
이 스킬은 이슈의 작성, 등록, 담당자 지정만 다룬다.

## 읽을 문서

- 작성 양식 : `Docs/Template/Issues Template.md`
- 섹션별 작성 규칙 : `Docs/Documentation/Github Issue Rule.md`

## 절차

1. **권유** : 업무가 이슈로 남길 만하다고 판단되면, 이유를 한 줄로 붙여 이슈 작성을 권유한다. 사용자가 원하지 않으면 이슈 없이 WorkflowRules의 `3. 브리핑`으로 넘어간다.
2. **정보 수집** : 업무 유형 (개발, 버그수정), 담당 영역 (UI, 맵, 사운드, 인스펙터), 관련 문서를 정리한다. 버그수정이면 재현 방법과 실제 동작, 기대 동작을 사용자에게 확인한다.
3. **초안 작성** : 양식과 작성 규칙에 따라 제목과 본문을 쓴다. 본문은 임시 파일로 저장해 둔다.
4. **승인** : 제목과 본문 전체를 사용자에게 보여 주고 승인을 받는다. 수정 요청이 오면 반영한 뒤 다시 보여 준다.
5. **등록** : 승인되면 GitHub CLI로 등록한다.

    ```bash
    gh issue create --title "[제목]" --body-file [본문 파일 경로] --label "[라벨]"
    ```

    - 라벨이 저장소에 없으면 `Docs/Documentation/Github Issue Rule.md`의 "라벨"을 따른다.
    - `gh`가 설치되어 있지 않거나 로그인이 안 되어 있으면 등록하지 말고, 사용자가 직접 등록할 수 있도록 제목과 본문을 전달한다.
6. **보고** : 등록된 이슈 번호와 주소를 알린다. 이후 PR에서 이 번호를 쓴다.

## 이슈에 착수할 때

- 사용자가 이슈에 착수하면 담당자를 사용자로 지정한다.

    ```bash
    gh issue edit [이슈 번호] --add-assignee @me
    ```

## 하지 않는 일

- 사용자 승인 없이 이슈를 등록하거나 수정하지 않는다.
- 이슈를 닫지 않는다. 이슈 닫기는 WorkflowRules의 `Issue Close` 단계에서 사용자와 함께 확인한다.
